# 电池供电下风扇与响应速度调查

用户反馈拔电后转速/噪音变化，菜单仍选曲线，同时显示“硬件读取失败，请稍后重试”。随后指出编辑器中的自定义响应速度开关关闭，原先约为 1000 ms/0.5%。

## 状态与曲线

检查时 AC0=0，BAT0 放电；系统服务运行，`last_error=0`，办公模式，曲线点仍为 `0 0 45 71 100 / 0 0 45 72 100`。产品代码没有按电源插拔切换风扇模式的逻辑。

先停止服务、卸载产品模块，再通过只读探针采集实际 EC 表；重载产品模块后先读取保留状态，最后才启动服务恢复偏好。实际 96 字节表符合当前曲线布局，没有被替换成默认表。控制位为 `0741=81, 0726=80, 0727=00, 07C5=88, 07C6=04, 0751=A0, 07C3=07, 0787=00`。注意 `0727.6` 已清除，因此不能把历史实验所用的全部控制位组合当成运行中的永久不变量。

电池供电下临时应用两路恒定 40% 曲线，性能模式保持办公，不发送周期即时 PWM。约 8 秒内两路 PWM 均收敛到 40%，RPM 约 2346/2395，CPU 54°C，`last_error=0`。随后恢复原曲线和系统服务。说明当前电池供电状态下 EC 仍能响应曲线设置；不支持“曲线表已恢复默认”的判断。

恢复原曲线后，在 CPU 约 53–54°C、GPU 休眠时观察到两路 PWM 约 25%，约 1500–1700 RPM。原曲线对应低温段为 0%。可能存在电池供电策略或其他固件约束；本次没有在同温度下成对测试 AC/DC，也没有定位所有内部温度和保护条件，因此不能将 25% 认定为已验证的固定最低转速，更没有以周期写 PWM 绕过固件行为。

证据：[原始表和状态](fan-power-dc-2026-11-10.log)、[40% 响应实验](fan-power-dc-response-2026-11-10.log)。

## 响应速度的保存与恢复

本轮检查前，偏好文件最后修改于 2026-11-10 13:43:46，保存的 `fan_response_ms` 为 `"0"`。先前 17:04 的插电快照也为 0，早于限充写入实验及用户拔电。本轮只读 EC 快照 `0787=00` 与此一致。现有证据无法确认用户之前启用的值何时变为关闭，不能直接归因于拔电或本轮限充测试。

受控验证当前安装的系统服务：将响应速度设为 600，确认硬件和偏好文件均为 600；重启服务后仍为 600；恢复初值 0，确认偏好文件字节内容与实验前完全一致。保存和服务启动恢复路径通过。

用户补充原值约 1000 且启用后，已显式设置为 **1000 ms/0.5%**，硬件、磁盘偏好和服务重启后的读回均为 1000。原曲线、办公模式保持，`last_error=0`。没有用截图中禁用控件的 100 ms 标签推断原值。已经打开的编辑器需点击“重新读取”来更新显示。

证据：[响应速度持久化与用户恢复记录](fan-response-persistence-2026-11-10.log)。

## 读取错误提示残留

扩展原先把状态读取错误与设置写入错误共用 `_error`；后续状态读取成功时没有清除它。此前诊断重载期间出现一次读取失败即可导致提示持续残留，即使后续温度和风扇读数已经恢复。截图符合此路径，但日志不能定位那一次失败的确切时间。

已将读取错误单独保存到 `_readError`，成功解析状态后自动清除，同时保留独立的写入失败提示。独立 GNOME UI 回归验证读取恢复不会清除写入失败信息，并通过现有菜单交互和布局测试。

修复已复制到安装目录；当前扩展已关闭再启用，清除旧实例的提示，状态 ACTIVE、扩展错误列表为空。GNOME 48 缓存已经导入的 JS 模块，当前会话不能保证载入新逻辑；完整修复在下次登录生效。本次没有重启整个桌面或要求用户立即注销。
