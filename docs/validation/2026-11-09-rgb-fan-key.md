# RGB、风扇与模式键验证

## RGB：通过

初始 EC RGB 为 (0,50,50)，模式 0x0767=0，亮度保持原值。短暂启用手动位，写入 (50,0,0)，保持 8 秒，读回成功。恢复 (0,50,50) 及原手动位成功。用户明确确认实际灯光变红并恢复青色。测试模块已卸载。

没有测试彩虹、渐变、分区/单键灯效或所有颜色组合。日志：`rgb-color-2026-11-09.log`。

## 风扇全速增强：通过

参考 tuxedo-drivers v4.25.0_rc 的 set_full_fan_mode，短暂置 0x0751 bit6，保留其他位。不修改风扇表或风扇 PWM 值。

- 初始：2126 / 2239 RPM，CPU 59°C，mode=0x20。
- 增强：约 4850 / 5010 RPM，mode=0x60。
- 恢复：原 mode=0x20、手动控制 bit0=0。
- 回落：2859/2994 → 2688/2822 → 2453/2658 → 2269/2401 → 2093/2209 RPM。
- 最后 CPU 56°C，模块已卸载。

验证范围是固件全速位与恢复原控制；不是任意目标 RPM、PWM 或自定义风扇曲线。原始日志：`fan-boost-2026-11-09.log`。

## 模式键

第一轮：WMI 观察器成功绑定事件 GUID，用户按键后未收到预期 0xB0；独立 EC 读取发现 0x0751 从 0x20 变成 0x30，手动位仍为 0、自定义配置位仍为 0。说明按键至少改变固件模式状态，不能再描述为 Linux 下完全无效。具体模式名称、性能效果和后续循环待验证。观察器已卸载。

第二次用户按键后：0x0751 从 0x30 返回 0x20，控制位 0x0741=0x80，自定义位 0x0727=0。这两次观察形成 0x20→0x30→0x20，仅确认两个状态；没有证据支持把它们直接命名成 Windows 三档。原始日志见 `mode-key-second-2026-11-09.log`。

第三轮，短暂启用 0x0741 bit0 后：观察器实际收到多次 WMI `0xB0`；用户反馈按键不再直接改变模式。观察器没有实现模式切换处理，因此这与“驱动接管后按键上报给操作系统”的路径一致。卸载时 gate_restore=0，随后独立只读确认 0x0741=0x80、0x0751=0x20、0x0727=0x00。RGB 恢复 (0,50,50)、亮度 4、充电配置 high_capacity；风扇自定义表使能仍为 0。所有诊断模块均已卸载。

日志：`mode-key-managed-2026-11-09.log`。后续后台服务若持有手动控制位，必须同时处理模式键/相关 Fn 行为，不能只接电池或灯光而默默改变按键行为。退出时释放控制权。具体 Windows 三档的名称与参数仍未知，不能把 `0xB0` 识别成功等同于三档策略验证成功。

## 后续原生三档循环：已确认状态与灯色

使用 `diagnostics/mode-native` 只读轮询，不启用手动位、不写 EC。用户逐次确认模式名称和模式键灯色，得到完整循环：

| 模式（用户确认） | 灯色 | 0x0751 |
| --- | --- | --- |
| 办公 | 绿色 | 0xA0 |
| 狂暴 | 紫色 | 0x30 |
| 均衡 | 蓝色 | 0x20 |

循环为办公→狂暴→均衡→办公。全过程 0x0741=0x80、0x0727=0、0x07c6=0。此前只观察到 0x20→0x30→0x20，不能据此认定固件只有两档；本轮补全了第三档。名称与指示灯已关联，实际功耗限制、性能差异和风扇策略尚未测量，软件主动写入三档也尚未验证。

参考驱动旧 profile_v1 的写入逻辑会清除 0xB0 掩码并设置 0xA0/0x00/0x10，而本机原生读数为 0xA0/0x20/0x30，且本机未列入该接口的 DMI 白名单。不能未经验证直接套用旧接口。

原始日志：`mode-native-cycle-2026-11-09.log`。测试结束停留在用户切回的办公模式，已卸载只读模块。

## 软件主动三档切换：读回及灯色通过

`diagnostics/mode-switch` 从办公 0xA0、控制位 0x80 开始，临时启用手动位，以 0xB0 掩码保留其余位，顺序写入均衡 0x20→狂暴 0x30→办公 0xA0。每档保持约 8 秒且每秒读回，全部通过，CPU 为 59–60°C。随后恢复原始模式和手动位，独立只读模块确认 0x0751=0xA0、0x0741=0x80、0x0727=0、0x07c6=0。

用户确认：“蓝色 变成了 紫色，现在是绿色”。至此软件写入、持续读回、模式灯色三者一致。未测量各档实际功耗限制和负载性能，也尚未实现收到 0xB0 后自动循环切换。测试模块和独立只读模块均已卸载。

原始日志：`mode-switch-2026-11-09.log`（使用内核单调时间；开头含此前只读探针记录，本轮从 `mechrevo_mode_test: BEFORE` 开始）。

## 模式键与软件切换联动

`diagnostics/mode-key-cycle` 临时接管后，三次物理按键分别收到 0xB0，并执行 0xA0→0x30→0x20→0xA0，三次写入读回 result=0，CPU 60°C。第三次自动恢复，complete restore=0。随后卸载并用独立只读探针确认 0x0751=0xA0、0x0741=0x80、0x0727=0、0x07c6=0。没有残留诊断模块。

这验证了事件→切换→读回→释放控制权的诊断路径。用户明确确认按键灯色为紫色→蓝色→绿色。此轮未触发超时、防抖或失败重试分支。尚未接入产品服务，也没有验证负载性能、休眠恢复和长时间运行。

日志：`mode-key-cycle-2026-11-09.log`。

## 超时恢复：通过

首次尝试用户连续按了多次，触发三次完成路径，不能计为超时验证。日志 `mode-key-timeout-attempt-2026-11-09.log`。

第二轮以 `timeout_seconds=60 timeout_only=1` 加载，只处理第一个按键，然后等待超时。初始已由用户切到狂暴 0x30；按键收到 0xB0 后切到均衡 0x20。约 60 秒超时恢复 0x30 和原控制位，timeout restore=0。用户确认看到蓝色自动恢复紫色。

卸载后独立探针确认 0x0751=0x30、0x0741=0x80、0x0727=0、0x07c6=0，RGB 和亮度等未变。没有残留诊断模块。此结果验证正常超时分支，不代表驱动崩溃、EC 写入失败或休眠恢复已通过。日志：`mode-key-timeout-2026-11-09.log`。
